# Изолированный исполнитель пакетов

`BatchExecutor` ещё не подключён к плагину: до проверки границы Desktop из задачи 1.2 реальные изменяющие операции запрещены. Экземпляр и `OperationJournal` принадлежат одной живой сессии. `submit` проверяет scope и общую схему до очереди, резервирует UUIDv7 в журнале и запускает пакеты последовательно. Повтор возвращает известное состояние или результат, не запуская запись. `get` читает живой журнал; `cancel` отменяет одну операцию, `stop` — все текущие и ожидающие. Отмена проверяется на границах шагов и доступна обработчику длительного шага через callback; прервать синхронный вызов API она не может.

Callbacks платформы отвечают за проверку документа и поколения (`checkScope`), загрузку страницы и шрифтов без записи (`prepare`), чтение фактических свойств после загрузки (`readExpected`), применение операции (`execute`) и границу Undo (`commitUndo`). `execute` обязан сообщать об изменении через `record` сразу после каждого успешного изменения, включая промежуточные изменения до возможной ошибки. Иначе исполнитель не сможет узнать об этом изменении. `commitUndo` вызывается после пакета с известными изменениями, включая частичный; глобальный Undo не вызывается. Эти callbacks и конкретные действия предстоит реализовать и проверить в Desktop.

`expected` сравнивается только по переданным полям, вложенные объекты и массивы сравниваются полностью, включая порядок. `readExpected` обязан получать живые значения объекта, который изменяет шаг, а не кэш, и выдавать `parentId` и упорядоченный `children` для структурных проверок; текстовые операции должны проверять `characters` и изменяемое форматирование, операции со стилями и переменными — изменяемые свойства и связи общего ресурса. Для перемещения, группировки и других действий с несколькими объектами `expected.related` задаёт отдельные предусловия по ID связанных объектов. Callback обязан возвращать для каждого объекта только запрошенные поля, включая вложенные значения; отсутствие объекта или поля считается конфликтом. Исполнитель сам не доказывает полноту предусловий и не обеспечивает блокировку от ручных правок между проверкой и записью.

Журнал ограничен сессией, допустимым возрастом ID и числом записей; он не сохраняется после перезапуска. `ExecutionTransport` при таймауте ожидания или обрыве возвращает полный конверт `unknown`, не отменяя внутреннее исполнение. После `reconnect` с новым поколением той же сессии команда с любым несовпадающим generation только ищет результат в журнале; если записи нет, возвращается `unknown`. `status` позволяет узнать результат, когда исполнение завершится. Идентичность payload присутствующей записи проверяется журналом. Новый sessionId и повтор текущего поколения при reconnect отклоняются; значения поколений непрозрачны и не обязаны возрастать. История поколений не хранится.

Интеграция обязана сохранять исходный scope каждой команды при reconnect: замена поколения старой команды на новое уничтожает различие между повтором и новой записью. Новый экземпляр плагина получает новый sessionId и новый журнал; потерянную команду из прежней сессии исполнять нельзя. Платформенный `checkScope` обязан также отклонять устаревшую очередь перед очередной записью. Helper пока не подключён к серверу и плагину; таймаут, лимиты, реальные callbacks и поведение Desktop требуют интеграции и проверки. Задачи 5.1–5.6 остаются открыты.
