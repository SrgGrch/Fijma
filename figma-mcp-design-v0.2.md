# Fijma — дизайн-документ

**Версия:** 0.2 · **Дата:** 3 ноября 2026 года  
**Статус:** решения D1–D5 согласованы; технические детали, требующие проверки, перечислены отдельно.  
**Область:** собственный MCP-сервер и локальный плагин для редактирования Figma Design ИИ-агентом. Код реализации и конфигурационные примеры не входят в документ.

## 1. Контекст и цель

Пользователю нужен инструмент, через который ИИ-агент сможет читать и редактировать дизайн в Figma: создавать новые экраны и изменять существующие, работать с компоновкой, текстом, визуальными свойствами и дизайн-системой.

Из обсуждения зафиксированы требования: собственный MCP-сервер, взаимодействие с локальным development-плагином Figma, доступ к основным возможностям редактирования документа. Для первой версии согласованы: все компоненты на одном компьютере; полная автономность агента при работе с текущим открытым файлом (YOLO, без диалогов подтверждения); только структурированные инструменты; без внешних библиотек, прототипирования и сложных векторов; один агент и один активный документ.

Цель — предоставить агенту управляемый интерфейс работы с документом, а не автоматизировать клики по интерфейсу Figma. Критерий успеха: агент понимает текущую структуру, выполняет изменения в явно выбранном документе и получает проверяемый результат, включая визуальное представление изменённой области.

## 2. Согласованные архитектурные решения

| ID | Тема | Решение для MVP |
|---|---|---|
| D1 | Размещение | Агент, MCP-сервер и Figma Desktop работают на одном компьютере; транспорт MCP — локальный `stdio`, мост — loopback WebSocket. |
| D2 | Автономность | **YOLO:** после запуска и подключения плагина агент может менять **весь текущий открытый документ** без подтверждений, включая удаление, массовые операции, локальные компоненты, стили и переменные. Утверждение отдельных команд пользователем не требуется. |
| D3 | Способ управления | Только **структурированные MCP-инструменты** со схемами параметров; поддерживаются пакетные изменения. Запуск произвольного JavaScript из команд агента запрещён. |
| D4 | Расширенные возможности | Внешние библиотеки, прототипирование и сложное редактирование векторных кривых не входят в MVP. Локальные компоненты, варианты, стили и переменные входят. |
| D5 | Параллельность | Одновременно обслуживаются **один активный файл и один MCP-клиент/агент**. Нет маршрутизации между несколькими открытыми документами. |

**Трактовка YOLO:** это отсутствие запросов на подтверждение правок, но **не** отключение проверки схем, валидации типов, ограничений API, привязки к сессии, обработки ошибок или защиты локального канала. Пользователь может остановить мост или закрыть плагин; выполненные изменения не откатываются автоматически.

**Область действия:** текущий документ целиком, а не выбранный фрейм. По смене документа или перезапуске плагина старая сессия аннулируется. Редактирование других файлов возможно только после открытия соответствующего файла и запуска в нём плагина; автоматического переключения между документами в MVP нет.

## 3. Проверенные границы платформы

Локальный development-плагин можно импортировать из manifest без публикации. Для этого Figma документирует использование Desktop-приложения для macOS или Windows; функция доступна на всех планах. Это не следует смешивать с организационным механизмом private plugins. [S1]

Plugin API предоставляет чтение и изменение содержимого документа. При этом отдельные возможности редактора, метаданные файла, комментарии и управление доступом не образуют универсальный интерфейс редактирования через Plugin API. Поэтому требование формулируется как «основные операции, доступные Plugin API», а не «полное повторение интерфейса Figma». [S2]

Плагин запускается пользователем и не является независимым фоновым сервисом. Для выбранной архитектуры нужен открытый файл и активный экземпляр плагина; закрытие плагина прекращает выполнение команд. Режим Dev Mode не подходит для изменения содержимого документа. [S2, S3, S4]

Выполняющая часть плагина имеет доступ к дереву документа. UI работает в iframe и обеспечивает доступ к браузерным механизмам, включая сетевое соединение. Между этими частями используется обмен сообщениями. Разрешённые сетевые адреса задаются в manifest; поддерживаются схемы ws и wss. [S3, S5]

Страницы загружаются динамически. Чтение другой страницы требует её загрузки, а операции с текстом — предварительной загрузки доступных редактору шрифтов. Не следует загружать весь документ для каждой команды. [S6, S7]

## 4. Принятая архитектура

**Агент / MCP-клиент ↔ MCP-сервер с модулем моста ↔ UI плагина ↔ выполняющая часть плагина ↔ документ Figma.**

MCP используется между клиентом и сервером. Между сервером и плагином предлагается отдельный внутренний протокол команд поверх WebSocket. Плагину не требуется самостоятельно реализовывать MCP.

В MVP используется локальный MCP-транспорт **stdio**. UI плагина инициирует **WebSocket** к мосту, слушающему только локальный loopback-адрес. Streamable HTTP и удалённые подключения отложены. Конкретная версия MCP и совместимость с выбранным клиентом проверяются при реализации. [S8]

### 4.1. MCP-клиент и агент

Клиент предоставляет модели инструменты. Агент анализирует запрос пользователя, читает контекст, формирует изменения и проверяет результат. Собственная LLM внутри сервера или плагина не требуется.

Агент не считается доверенным источником корректных команд. Он не должен определять права сам для себя: фиксированные полномочия MVP задаются режимом полного доступа к текущему документу. Содержимое документа, включая текст слоёв и названия, трактуется как данные, а не как команды, меняющие настройки соединения или расширяющие доступ на другие файлы.

### 4.2. MCP-сервер

Сервер отвечает за каталог инструментов, проверку параметров, выбор сессии, маршрутизацию команд, управление очередью, ограничения ресурсов, журнал операций и возврат результата клиенту.

В первой версии MCP-адаптер и WebSocket-мост работают в одном процессе, но разделяются логически. Это позволяет позднее добавить другой MCP-транспорт или вынести обслуживание соединений, не переписывая обработчики операций.

Сервер не хранит независимую редактируемую копию макета. Его кэш служит только ускорению чтения. Источником истины остаётся живой документ Figma.

### 4.3. UI плагина

UI инициирует соединение с сервером, выполняет сопряжение и передаёт команды выполняющей части. В интерфейсе отображаются состояние подключения, текущий документ, режим **Full-document / YOLO**, текущая операция и последние ошибки.

Пользователь может отключить запись, разорвать соединение и остановить последующие операции. Диалогов подтверждения массового удаления или иных изменений в MVP нет; управление осуществляется только явным запуском/остановкой плагина и соединения.

UI не является местом изменения дерева документа и не должен содержать вторую реализацию бизнес-правил редактирования.

### 4.4. Выполняющая часть плагина

Это единственный компонент системы, изменяющий документ. Он повторно проверяет тип команды, актуальность сессии, соответствие текущему документу, доступность узлов и допустимость свойств непосредственно перед выполнением.

Обработчики разделяются по функциональным областям: чтение, структура, компоновка, текст, оформление, компоненты, переменные, ресурсы и экспорт. Общими остаются проверка области, загрузка зависимостей, нормализация ошибок и сбор результата.

## 5. Функциональный охват

Ниже приведён согласованный целевой охват MVP, а не обещание доступа ко всем функциям Figma. Базовые типы узлов и их свойства описаны в документации Plugin API; операции должны учитывать конкретный тип узла и ограничения редактора. [S9, S10]

| Область | Возможности MVP |
|---|---|
| Чтение и навигация | Страницы, текущая страница и выделение; дерево с ограничением глубины; поиск; свойства узлов; выбор и показ узлов пользователю. |
| Структура | Создание, переименование, клонирование, перемещение и удаление страниц и поддерживаемых узлов; группировка; изменение родителя и порядка слоёв. |
| Компоновка | Размеры и позиция; constraints; Auto Layout; отступы, промежутки, выравнивание, перенос и режимы размеров. |
| Текст | Создание и изменение текста, параметров типографики и форматирования диапазонов с сохранением незатронутых участков. |
| Оформление | Заливки, градиенты, обводки, прозрачность, скругления, эффекты; создание и применение локальных стилей. |
| Компоненты | Создание локальных компонентов и наборов вариантов; создание экземпляров, изменение свойств и переключение вариантов; явная, а не автоматическая операция отделения экземпляра. |
| Переменные | Локальные коллекции, переменные, значения по режимам, aliases и привязки к поддерживаемым свойствам. |
| Изображения и графика | Добавление изображений и SVG, базовые фигуры, поддерживаемые булевы операции. |
| Проверка результата | Повторное чтение изменённых узлов, размеры и границы; изображение выбранного фрейма; экспорт PNG/SVG. |

Работа с локальными переменными и их привязками опирается на API variables. Конкретная доступность режимов и операций проверяется во время выполнения; ограничения не обходятся молчаливой заменой переменных на константы. [S11]

Для визуальной проверки используется экспорт узла, а не снимок интерфейса рабочего стола. Передача изображения модели зависит от возможностей MCP-клиента и агента; структурное чтение остаётся обязательным независимо от этого. [S12]

### 5.1. Отложенные возможности (D4)

**Внешние библиотеки.** В MVP поддерживаются компоненты и стили внутри открытого файла. Импорт ресурсов из внешних библиотек отложен; нельзя предполагать, что плагин может перечислить и изменять любые ресурсы организации. [S2]

**Прототипирование.** Чтение и редактирование интерактивных переходов, триггеров и реакций отложено. API описывает реакции через триггеры и действия; поддержка может быть добавлена отдельным набором инструментов. [S13]

**Сложные векторы.** Детальное редактирование кривых и сетей отложено; базовые фигуры, SVG, изображения и поддерживаемые булевы операции остаются в MVP.

### 5.2. Что не входит в предлагаемую первую версию

Не включаются работа с закрытыми файлами без активного плагина, публикация библиотек, администрирование команд и прав, замена системы версий Figma, FigJam/Slides/Buzz и автоматизация интерфейса мышью. Отдельная интеграция с REST API не требуется для основного канала редактирования и рассматривается только при появлении соответствующих требований.

## 6. Интерфейс инструментов агента

Используется ограниченное число предметных групп инструментов с явными схемами параметров. Это не один универсальный инструмент «изменить что угодно» и не отдельный инструмент на каждое свойство каждого узла.

Инструменты чтения отдельно описывают запрос структуры, поиск, получение свойств и экспорт. Инструменты записи отдельно описывают создание, обновление, перемещение, удаление и операции дизайн-системы. Сервер возвращает агенту фактический список поддерживаемых возможностей.

Для связанных изменений обязателен пакетный инструмент. Он принимает последовательность декларативных операций, поддерживает ссылки на узлы, созданные ранее в том же пакете, и возвращает результат каждого шага. По умолчанию выполнение прекращается после первой ошибки; уже выполненные шаги явно перечисляются.

Произвольный JavaScript не входит в MVP. Он увеличил бы охват API, но потребовал бы отдельной модели доверия: нельзя одновременно обещать произвольный доступ к Plugin API и гарантировать все ограничения, проверяемые только структурированными обработчиками. Доверенный режим выполнения кода, если он нужен, проектируется отдельно и не включается скрыто как запасной путь.

## 7. Сессии и привязка к документу

Каждый запуск плагина получает идентификатор сессии и новое поколение подключения. Команда всегда адресуется конкретной сессии, а идентификаторы узлов интерпретируются только в её контексте. Название файла не является уникальным идентификатором.

Не следует строить обязательную маршрутизацию вокруг `figma.fileKey`: документация ограничивает его доступность private plugins и ресурсами Figma. Локальная установка сама по себе не является основанием предполагать доступ к этому полю. Для работы моста достаточно собственной сессии; сведения о файле используются для отображения и дополнительной проверки. [S14]

UI показывает имя текущего открытого документа, режим полного доступа и статус моста. После запуска плагина нет отдельной процедуры согласования области. Если одновременно обнаружены несколько сессий или клиентов, сервер **не выбирает произвольно одну из них**: в MVP он отклоняет второе подключение или останавливает запись до устранения неоднозначности.

Перезапуск плагина аннулирует старые команды. После восстановления соединения клиент повторно получает контекст и актуальную привязку к активному документу; отдельное пользовательское подтверждение не нужно. Команды предыдущего поколения не должны исполняться в новом файле или новой сессии.

## 8. Внутренний протокол и выполнение команды

Протокол моста версионируется отдельно от MCP. При подключении стороны обмениваются версиями, перечнем возможностей, ограничениями размера сообщений и состоянием сессии. Несовместимость блокирует команды, а не приводит к попытке угадать формат.

Каждый запрос содержит идентификатор операции, адрес сессии, тип команды, параметры и при необходимости ожидаемое исходное состояние. Область действия в MVP фиксирована: весь активный документ. Ответ содержит статус, результаты шагов, идентификаторы затронутых узлов, предупреждения и структурированную ошибку. Подтверждение получения не означает успешного выполнения.

Последовательность обработки: проверка схемы запроса → проверка сессии и текущего документа → постановка в очередь → передача плагину → повторная проверка и загрузка зависимостей → выполнение → проверка результата → возврат ответа агенту. Шаги согласования изменений с пользователем отсутствуют.

Для операций предлагаются состояния: в очереди, выполняется, успешно, ошибка, частично выполнено, отменено и результат неизвестен. Последнее состояние необходимо, когда соединение оборвалось после возможного изменения документа, но до получения подтверждения.

Предварительная проверка может обнаружить неподдерживаемые параметры, отсутствующие шрифты или неверную сессию. Она не считается точным визуальным предпросмотром и не резервирует документ от чужих изменений.

## 9. Надёжность и совместное редактирование

### 9.1. Последовательная запись

Внутри одной сессии выполняется одна изменяющая операция за раз. Это устраняет гонки между командами самого моста, но не блокирует ручные правки пользователя и действия других участников Figma.

Для чувствительных операций проверяются ожидаемые значения или отпечатки значимых свойств. При несовпадении возвращается конфликт и требуется повторное чтение. Это оптимистическая проверка, а не полноценная транзакционная изоляция.

### 9.2. Повторы и потеря связи

В пределах живой сессии плагин хранит результаты недавно выполненных операций по их идентификаторам. Повтор того же запроса возвращает известный результат, а не повторяет создание объектов.

Гарантия не распространяется автоматически на перезапуск плагина. После потери подтверждения сервер не должен вслепую повторять запись. Сначала запрашивается состояние операции и перечитывается документ; при отсутствии достаточных данных результат остаётся неизвестным. Гарантия exactly-once через все виды сбоев не заявляется.

### 9.3. Частичные изменения и Undo

Пакет не объявляется атомарной транзакцией. Ошибка на позднем шаге может оставить ранее выполненные изменения. Возвращаемый результат должен позволять понять, что выполнено и что требует исправления.

Plugin API позволяет устанавливать границы истории Undo через `commitUndo`. Предлагается использовать их между логическими пакетами, а поведение при совместном редактировании проверить отдельно. Это не заменяет журнал результатов и не является гарантией универсального отката. [S15]

Автоматически вызывать глобальный Undo при любом сетевом сбое не следует: состояние могло измениться. Компенсирующие действия допустимы только для явно поддержанных операций и после проверки текущего состояния. Для рискованных массовых правок пользователь может предварительно работать с копией страницы или файла.

### 9.4. Область доступа и побочные эффекты

В MVP агент имеет право изменять **всё содержимое текущего открытого файла**. Ограничений на отдельные страницы, фреймы и элементы нет. Допускаются массовое удаление, операции над локальными главными компонентами, стилями и переменными, даже если их изменения затрагивают многие экраны того же документа.

Граница полномочий — **текущая сессия плагина и её открытый документ**. Команда не должна перенаправляться в другой файл из-за переключения вкладки, переподключения или совпадения названий. Ошибки Figma API, блокировки и ограничения типов не обходятся. Мост сообщает о широких побочных эффектах в результате операции, если их удалось определить, но не требует подтверждения.

## 10. Безопасность и контроль пользователя

Для локального режима сервер моста слушает только loopback-интерфейс. Даже локальному соединению требуется сопряжение с секретом сессии; одного известного порта недостаточно для авторизации. Секреты не возвращаются агенту как содержимое инструментов и не попадают в журналы.

Сетевые адреса ограничиваются manifest плагина. На сервере проверяются соединения и сообщения; особенности origin iframe учитываются при реализации, но origin не заменяет аутентификацию. Произвольные внешние адреса и загрузка ресурсов по указанию текста из документа по умолчанию не разрешаются.

При добавлении удалённого режима потребуется отдельная модель аутентификации клиента и плагина, шифрование канала, разграничение пользователей и защита HTTP-интерфейса. Открытие локального WebSocket-порта в интернет не считается допустимым способом реализации этого режима.

**Режим YOLO:** после активного подключения плагина любые поддерживаемые операции над открытым файлом исполняются без запроса подтверждения, в том числе удаление страниц/элементов, отделение экземпляров, изменение локальных общих компонентов, стилей и переменных. Никаких дополнительных approval-шагов в MCP-сервере и UI нет. Это не разрешает выполнение произвольного кода и не распространяется на другие файлы или внешние библиотеки.

Команда остановки прекращает очередь и дальнейшие шаги, но не отменяет уже выполненные изменения. Отмена длительного синхронного участка может быть не мгновенной; поэтому объём отдельных участков должен быть ограничен.

Локальный мост не означает, что данные никогда не покидают компьютер: выбранный пользователем агент может отправлять контекст и изображения внешнему поставщику модели. Объём передаваемых данных должен быть управляемым.

## 11. Производительность, ресурсы и диагностика

Чтение строится по принципу постепенного раскрытия: сначала обзор страниц и фреймов, затем нужное поддерево, затем конкретные свойства. Запросы имеют ограничения глубины, количества узлов и размера ответа; поиск поддерживает продолжение. Полная сериализация документа на каждом шаге не требуется.

Изображения и экспорты имеют ограничения разрешения и объёма. Крупные результаты предлагается передавать отдельными ресурсами либо порциями; способ выдачи согласуется с поддержкой MCP-клиента. Временные файлы имеют ограниченный срок хранения.

Кэш связывается с сессией и инвалидируется при наблюдаемых изменениях. Для записи значимые свойства перечитываются непосредственно перед изменением. События документа используются как подсказки для актуализации, а не как доказательство глобальной транзакционной версии.

Журнал содержит идентификатор операции, сессию, тип действия, длительность, статус и идентификаторы затронутых узлов. Текст макетов, изображения и секреты по умолчанию не записываются. Диагностический режим с дополнительными данными включается явно.

Ошибки должны различать отсутствие подключения, истёкшую сессию, недопустимые аргументы, попытку обращения к другому документу, отсутствующий узел, недоступную возможность, проблему шрифта, конфликт, частичное выполнение и неизвестный результат. Агент получает рекомендации по восстановлению, не позволяющие автоматически подключаться к другим документам.

## 12. Предлагаемые этапы реализации

**Основа.** Локальное подключение, сопряжение, сессии, чтение документа, поиск и экспорт. Проверяется реальное соединение Desktop-плагина с выбранным транспортом и поведение при отключениях.

**Основное редактирование.** Структура, оформление, текст, Auto Layout, пакетные операции, обработка конфликтов и границы Undo; весь активный документ доступен на запись.

**Дизайн-система.** Локальные компоненты, варианты, экземпляры, стили, переменные и режимы. Этот этап входит в предлагаемую полноценную первую версию: инструмент не должен оставаться только генератором прямоугольников и текста.

**Отложенные расширения.** Внешние библиотеки, прототипирование, сложные векторы, несколько документов, несколько агентов и удалённый доступ. Выполнение произвольного кода не рассматривается в рамках MVP и требует нового архитектурного решения.

## 13. Критерии приёмки

| Сценарий | Ожидаемый результат |
|---|---|
| Работа с существующим экраном | Агент читает структуру, изменяет текст и Auto Layout, сохраняет незатронутое форматирование и получает изображение результата. |
| Создание нового экрана | Созданы настоящие редактируемые узлы, а не единая картинка; возвращены их идентификаторы. |
| Компоненты и переменные | Изменения сохраняют связи, варианты и привязки; отделение экземпляров и замена токенов константами не происходят молча. |
| YOLO / полный документ | Агент без подтверждений редактирует любую страницу и локальные общие ресурсы в активном документе, включая массовое удаление; другие файлы недоступны. |
| Отсутствующий шрифт или операция | Возвращается понятная ошибка или предупреждение; не выполняется скрытая подмена. |
| Потеря ответа | Повтор в живой сессии не создаёт дубликатов; после потери состояния сообщается неопределённость. |
| Ошибка в пакете | Указаны выполненные шаги и оставшиеся изменения; атомарный откат не заявляется. |
| Ручное изменение во время работы | Существенный конфликт обнаруживается проверкой исходного состояния; агент не перезаписывает его молча. |
| Перезапуск плагина | Старые команды отклоняются; требуется привязка к новой сессии без отдельного подтверждения пользователя. |
| Остановка пользователем | Новые и ожидающие изменения прекращаются; уже применённые изменения явно отмечены. |
| Большой документ | Ограниченное чтение не требует полной загрузки и передачи всего файла. |

Дополнительно проверяются пустой файл, смешанные шрифты, скрытые и заблокированные слои, ограничения структуры экземпляров, недоступные библиотечные ресурсы, попытка второго подключения, смена вкладки и повторное подключение после сбоя.

## 14. Открытые технические проверки

До утверждения реализации нужны короткие проверочные эксперименты: поведение loopback-соединения и сетевой политики на целевой ОС; жизненный цикл плагина при смене вкладок; границы Undo при ручных правках; доступность выбранных операций для используемой лицензии; доставка экспортированных изображений выбранному MCP-клиенту.

Точные лимиты размера пакета, числа узлов, таймаутов и срока хранения результатов задаются после этих проверок. Они не должны маскироваться под гарантии платформы.
