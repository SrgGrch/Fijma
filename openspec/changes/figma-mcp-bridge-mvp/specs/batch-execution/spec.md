# Надёжное выполнение пакетов

## Purpose

Обеспечить последовательное и наблюдаемое изменение документа без обещания атомарности или exactly-once за пределами живой сессии плагина.

## ADDED Requirements

### Requirement: Последовательная запись
Система MUST исполнять одну изменяющую операцию за раз внутри сессии, включая все шаги пакета. Проверка схемы и сессии MUST предшествовать очереди; актуальность сессии, узлов и параметров MUST повторно проверяться перед записью.

#### Scenario: Два одновременно полученных пакета
- **WHEN** агент отправил два пакета до завершения первого
- **THEN** их изменяющие шаги не перемешиваются и второй исполняется только после завершения или остановки первого

### Requirement: Ссылки на результаты шагов
Пакет MUST принимать упорядоченные декларативные шаги с уникальными stepId и ссылками на ранее созданные объекты. Дубликаты stepId, ссылки вперёд и несовместимые типы ссылок MUST отклоняться до начала записи.

#### Scenario: Фрейм и его текст
- **WHEN** первый шаг создаёт фрейм, а следующий создаёт текст со ссылкой на этот шаг как parent
- **THEN** текст помещается в созданный фрейм, а ответ содержит соответствие stepId фактическим nodeId

#### Scenario: Некорректная ссылка
- **WHEN** пакет ссылается на несуществующий или последующий шаг
- **THEN** пакет получает INVALID_ARGUMENT без выполнения первого шага

### Requirement: Остановка после ошибки
По первой ошибке система MUST прекращать оставшиеся шаги и возвращать результат каждого шага, включая неприменённые. Пакет MUST NOT объявляться атомарным; изменения, сделанные даже внутри неуспешного шага, MUST учитываться, если известны.

#### Scenario: Ошибка на позднем шаге
- **WHEN** создание фрейма завершилось, а добавление текста не удалось из-за шрифта
- **THEN** ответ partially_applied перечисляет созданный фрейм, неуспешный шаг и пропущенные шаги без заявления об откате

### Requirement: Проверка исходного состояния
Изменение/удаление существующих объектов MUST проверять ожидаемые значимые свойства или их отпечаток непосредственно перед записью. Совпадение MUST NOT трактоваться как блокировка ручного редактирования; конфликт MUST требовать нового чтения.

#### Scenario: Пользователь изменил текст
- **WHEN** ожидаемый текст в команде отличается от живого текста
- **THEN** шаг возвращает CONFLICT без перезаписи текста; предыдущие шаги пакета остаются перечислены

#### Scenario: Перемещение изменившегося узла
- **WHEN** ожидаемый родитель или порядок детей уже изменён другим участником
- **THEN** перемещение отклоняется как конфликт и не пересчитывается молча относительно новой структуры

### Requirement: Дедупликация живой сессии
Плагин MUST хранить ограниченный журнал по sessionId и operationId. Повтор идентичного запроса MUST возвращать известный статус/результат; тот же ID с иным содержимым MUST давать OPERATION_ID_CONFLICT. Срок хранения и границы гарантии MUST быть опубликованы.

#### Scenario: Повтор после потери ответа
- **WHEN** результат создания потерян, но идентичная операция ещё есть в журнале живого плагина
- **THEN** возвращается прежний результат с теми же nodeId, новые объекты не создаются

#### Scenario: Повтор выполняющейся команды
- **WHEN** идентичный запрос повторён до окончания исходной команды
- **THEN** возвращается queued или running исходной операции без запуска второго исполнения

### Requirement: Восстановление неизвестного результата
После потери подтверждения система MUST NOT вслепую повторять запись. Она MUST предоставлять запрос состояния операции и повторное чтение документа; при отсутствии доказательств результат MUST оставаться unknown. Истечение журнала MUST NOT разрешать повторное исполнение старого operationId.

#### Scenario: Перезапуск уничтожил журнал
- **WHEN** связь потеряна после возможной записи, а плагин перезапущен до выяснения результата
- **THEN** агент получает unknown, перечитывает новую сессию и не получает автоматического повтора старой записи

#### Scenario: Истёк срок результата
- **WHEN** предъявлен старый ID за пределами объявленного окна дедупликации
- **THEN** возвращается OPERATION_EXPIRED или unknown, а не повторное создание

### Requirement: Отмена без отката
Остановка пользователем или отмена операции MUST прекращать ожидающие команды и дальнейшие шаги на ближайшей доступной границе. Уже применённое MUST возвращаться явно; ограниченные синхронные участки MUST NOT обещать мгновенную отмену.

#### Scenario: Отмена выполняющегося пакета
- **WHEN** отмена поступила после успешного первого шага
- **THEN** следующий шаг не запускается, ответ cancelled перечисляет применённое и неприменённое без автоматического Undo

### Requirement: Границы Undo
Система MUST разделять логические пакеты границами истории Undo, используя поддерживаемое API Figma. Ошибка и отключение MUST NOT автоматически вызывать глобальный Undo; поведение при совместных правках MUST быть проверено в Desktop.

#### Scenario: Два успешных пакета
- **WHEN** пользователь вызывает Undo после двух завершённых пакетов в проверенной конфигурации без промежуточных ручных правок
- **THEN** отменяется последний пакет в соответствии с проверенным поведением Figma, а первый остаётся; результат эксперимента зафиксирован

#### Scenario: Сбой после ручных изменений
- **WHEN** связь оборвалась после записи и ручной правки пользователя
- **THEN** мост не вызывает глобальный Undo и сообщает известные изменения либо unknown
