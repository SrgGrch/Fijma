# Проверка shared-local-bridge

Дата: 5 ноября 2026. Среда: Windows, Node.js 22.23.2.

## Реализация

Обычная команда сервера теперь запускает stdio-адаптер общего процесса. Конфигурация Codex и endpoint плагина сохраняются. Общий процесс использует защищённый IPC, отдельные MCP-сессии и одного владельца документа. Есть аутентифицированная остановка `--stop-bridge` / `npm stop`. Изолированный режим FIGMA_MCP_PORT=0 сохранён, зависимости не добавлены.

## Автоматические проверки

- `npm test`: exit 0, весь существующий набор и четыре новых набора проверок.
- `node tests/manual-client.mjs`: exit 0.
- `openspec validate shared-local-bridge --strict`: успешно.
- `git diff --check`: успешно; предупреждения Git о LF/CRLF не являются ошибками diff.
- После сохранения прежнего принудительного выхода по сигналу в изолированном режиме повторно выполнены сборка сервера и smoke test.

Новые проверки:

- `catalog-ownership.mjs`: initialize/discovery/ping доступны, все 10 инструментов и чтение ресурса отклоняются до обработчика при SESSION_BUSY.
- `ipc-auth.mjs`: реальный IPC socket, взаимная аутентификация, неверный ключ, поддельный endpoint, replay, несовместимая версия, лимиты кадра/времени, отсутствие ключа в передаче, сохранение MCP-байтов после handshake.
- `adapter-startup.mjs`: отказ spawn, detached/windowsHide/независимые stdio, отсутствие повторного spawn при ошибке аутентификации или версии.
- `shared-bridge.mjs`: отдельные процессы и настоящий MCP SDK, одновременный запуск, общий PID, насыщение незавершённой аутентификации без вытеснения действующего клиента, закрытие не-владельца, передача после EOF и SIGKILL владельца, большой SVG-ресурс через IPC, изоляция экспорта, остановка/перезапуск, авария daemon, занятый порт и ошибка публикации IPC с освобождением WebSocket-порта.

Runtime плагина выполнялся в существующем VM harness. Обрыв владельца проверен после одного применённого шага активного пакета и при наличии ожидающего пакета: применённый шаг сохранился, последующие шаги и ожидающий пакет не исполнились; новое поколение, выключенная запись, отклонение прежнего scope и прежнего экспорта подтверждены. Это автоматическая проверка с имитацией Plugin API, а не нативная Desktop-приёмка.

Процессные тесты используют собственные каталоги и временные порты; после завершения тестовые daemon и каталоги удалены. Существующий каталог `test2/` не изменялся.

## Переход рабочего порта

Перед переходом проверена командная строка старого процесса 61332: это `node.exe` с entrypoint данного проекта, без режима общего моста. На 55263 были только listener и ни одного Established-подключения плагина. Остановлен только этот подтверждённый старый сервер; родительский Codex не завершался.

На реальном рабочем порту 127.0.0.1:55263 проверены двумя SDK-клиентами и отдельными stdio-адаптерами: общая инициализация и 10 инструментов, один PID, SESSION_BUSY, передача владения после закрытия первого клиента, явная остановка, новый запуск и повторное использование нового общего процесса. stdout команд остановки пуст. Ключ не выводился и не заменялся.

После окончательной сборки проверка рабочего порта повторена. Общий мост оставлен работающим (PID: 47372), адаптеры проверки закрыты, документ никому не принадлежит. Режим общего процесса сохраняет состояние уже запущенного кода; после следующего обновления сборки его необходимо перезапустить через `npm stop` и новое MCP-подключение.

Postman CLI 1.76.0 не поддерживает рекомендованную навыком команду `postman status` (unknown command). Postman workspace/HTTP-коллекции для этого локального IPC не использовались; эта ошибка не является результатом тестирования моста. Проверки контракта выполнены настоящим MCP SDK и процессными тестами выше.

## Диагностика зависания после paired

В Figma Desktop 126.11.7 воспроизведён цикл «Подключаемся… / Ждём локальный мост». Сервер принимал ключ и отправлял paired, но не получал hello в течение 5 секунд. Ошибок в консоли не было, потому что UI молча отбрасывал сообщения main по проверке event.source.

Временная диагностика только со счётчиками подтвердила: main запущен, runtime готов, hello-request получен, hello отправлен в UI; источником сообщений был window.top, а не непосредственный parent. До исправления наблюдались 4 запроса/ответа hello при 11 сообщениях от top и 0 от parent. Содержимое сообщений, ключ и данные документа не выводились.

В plugin/ui.ts разрешён подтверждённый источник window.top наряду с прежними parent/null. Схемы сообщений, фазовые проверки, проверка scope и отказ посторонним фреймам сохраняются. Пробное разрешение self убрано: оно не объясняло наблюдавшийся сбой.

Регрессионные проверки в remembered-pairing.mjs воспроизводят parent/top/null и отклонение чужого фрейма, включая загрузку ключа, отправку hello и переход в ready с выключенной записью. Пробное разрешение self не устранило нативный сбой; окончательное исправление основано на наблюдении сообщений от top. После окончательного изменения прошли сборка plugin/candidate, remembered-pairing, plugin-handshake, ui-validation, plugin-artifacts, full-bridge и candidate-recovery.

После перезапуска обычной сборки пользователь подтвердил успешное подключение. Временные перехватчики и диагностические файлы удалены, сервер возвращён в обычный фоновый режим. Настоящий SDK-клиент затем получил от подключённого плагина Figma `state=ready`, `writeEnabled=false` и действующий sessionId. Документ при проверке не изменялся; ключ остался прежним. Это нативное подтверждение восстановления handshake, отдельно от VM-тестов.

После окончательного исправления источника top повторный полный `npm test` завершился с exit 0; `openspec validate shared-local-bridge --strict` и `git diff --check` также прошли.

## Фоновая работа с закреплённым файлом

5 ноября пользователь явно выбрал продолжение работы с исходным файлом даже при открытии другой вкладки Figma. Новый контракт в shared-bridge заменяет прежнее отключение скрытого UI из MVP. В Plugin API не найден штатный сигнал, надёжно отличающий смену приложения от смены активного файла; недокументированные события, сопоставление по имени и эвристики фокуса не используются.

Из UI удалены отключение по visibilitychange и запреты подключения/повторных попыток при document.hidden. Скрытие не сбрасывает scope, запись или очередь. Обработчик pagehide, Stop, ручные Disconnect/Forget и сброс при потере MCP-владельца сохранены. Проверки sessionId/connectionGeneration и идентичности figma.root остаются: смена привязки требует явного подключения, а изменение самого корня не перенаправляет команды автоматически.

Автотесты подтвердили: подключение и сетевое восстановление скрытого UI, сохранение writeEnabled и поколения при скрытии/возврате, успешную запись через скрытый UI, сохранение running и queued операций при повторном скрытии, а также их остановку при настоящей потере владельца. Полный `npm test` завершился с exit 0; после усиления проверки running/queued отдельно повторно прошёл `node tests/shared-bridge.mjs`. Строгая проверка OpenSpec и `git diff --check` прошли.

После перезапуска плагина пользователь сообщил, что вернулся в Codex и оставил Figma в фоне. Реальный SDK-клиент выполнил 12 последовательных запросов контекста и 3 чтения дерева примерно за 12 секунд: все ответы ready, sessionId, connectionGeneration и подключённый файл неизменны. writeEnabled оставался false; документ не изменялся. Фоновая запись проверена в VM/процессных тестах, отдельная нативная запись и нативное переключение File A → File B в этом проходе не выполнялись.

Проверочный MCP-клиент завершён; это освобождает владение по существующим правилам и может вызвать одно переподключение плагина. Этот сброс относится к закрытию владельца, а не к скрытию окна. Обычный общий мост оставлен работающим, временная диагностика не устанавливалась.

## Объединение с аудитом MCP

При публикации коммита фоновой работы 3331d5a в origin/master уже находился merge аудита f63fed8. Объединены компактные схемы инструментов, экспорт PNG без дублирования байтов в тексте/structuredContent, оптимизации чтения ресурсов и границы readback. Сохранены общий процесс, контроль владельца, инструкции подключения, приём сообщений от window.top и фоновая работа с закреплённым файлом.

Конфликт восстановления разрешения записи разрешён в пользу согласованной здесь границы: скрытие UI сохраняет запись, но реальный обрыв и смена MCP-владельца не передают разрешение новому соединению. Автоматическое восстановление writeGranted из аудита не перенесено; тест восстановления после рестарта сохранён с writeEnabled=false и явным повторным включением записи.

На объединённой версии полный `npm test` завершился с exit 0; проверка staged diff прошла. Повторная нативная Desktop-приёмка после объединения не выполнялась, рабочий общий мост не перезапускался. Посторонний каталог test2/ в коммиты не включён.
