# Design

## Context

Мотивация: [proposal.md](proposal.md). Анализ выполнен по `0b0d6a7` (2026-11-05); продуктовый код не менялся и Desktop-пробы в этом исследовании не выполнялись.

Существующая основа:

| Область | Что уже есть | Что требуется |
| --- | --- | --- |
| `shared/contracts.ts`, `protocol.ts`, `context.ts`, `ui-messages.ts`, `bootstrap-limits.ts` | Строгие схемы, версия протокола 1, whitelist capabilities | Execute input/output, тип операции, разрешение, лимиты и версия 2 |

| `plugin/bridge-runtime.ts`, `bridge-controller.ts`, `ui.ts`, `ui.html` | Захват `figma.root`, writeEnabled, Stop, сообщения | Исполнение и отдельное разрешение, отображение привязанного файла, lifecycle |

| `plugin/manifest.json`, `main.ts`, `candidate.ts`, `scripts/*`, `package.json` | dynamic-page, loopback-only, esbuild 0.28.2, typings 1.142.0 | Согласованные сборки, compiler/catalog artifacts, проверки |

Тесты уже проверяют точное число 10 инструментов, схемы, handshake, ownership, размеры и типы ресурсов: `catalog-contracts`, `catalog-ownership`, `shared-bridge`, `protocol`, `message-limits`, `ui-validation`, `operation-result-contracts`, `batch-executor`, `export-*`, `candidate-*`. Их fixtures и ожидания — часть изменения, не только новые тесты.

Есть явный конфликт спецификаций: `figma-mcp-bridge-mvp/specs/structured-tools` запрещает произвольный код глобально; `scene-editing` запрещает обход неподдерживаемой команды; `openspec/config.yaml` описывает прежний запрет. Предложение заменяет только глобальный запрет отдельным opt-in инструментом. Внутри batch запрет и отсутствие fallback сохраняются. Старые положения о видимой вкладке нельзя переносить на нынешний background bound-file режим из `docs/launch.md`. До архивации согласовать эти документы; прошлые результаты приёмки не переписывать как новые доказательства. `shared-local-bridge/tasks.md:4.2` ещё не отмечен выполненным.

## Goals / Non-Goals

**Goals:** доступ к поддерживаемому API без новых предметных команд; ограниченные JSON/логи; повтор без повторной записи; отсутствие конкуренции с batch у корректного доверенного кода.

**Non-Goals:** безопасность против враждебного JavaScript, гарантированное read-only, hard timeout, rollback, полный список изменений, npm imports, работа в нескольких документах. Ограничение областью выбранного раздела — обязанность скрипта, а не граница безопасности.

## Decisions

### 1. Контракт и минимальный frontend

Рабочее имя `figma_execute`, без второго alias `fijma_execute`. Вход: `{scope, operationId, language: 'javascript'|'typescript', code, args?: JSON}`. `code` — тело async-функции с `return`; доступны настоящий `figma`, JSON `args`, локальный `console` и небольшой `execution` с `checkCancelled()`/`yield()`. Нет произвольных путей файлов, Node execution, imports или пользовательского endpoint.

UI получает один переключатель «Разрешить доверенный код» с кратким объяснением прав и ограничений Stop. Он выключен по умолчанию; writeEnabled для batch остаётся отдельным. Разрешение execute означает возможность записи даже у аналитического скрипта. Не вводить ложный `readOnly: true` или подтверждение каждого запроса.

### 2. Компиляция и реальная среда

Преобразовать TS на сервере установленным esbuild; не исполнять исходник на сервере. Это синтаксическое преобразование, НЕ проверка типов. Полную диагностику типов не включать в первую поставку; каталог и примеры использовать с закреплёнными typings. Если esbuild нужен при запуске — перенести его в runtime dependencies и проверить production install, не добавлять другой компилятор.

Plugin main выполняет полученный JS через проверенный Desktop-пробой механизм динамического выполнения. Официальные материалы подтверждают eval, но отмечают отличия поведения; выбор wrapper, async и source mapping закрепляется пробой до основной реализации. Не считать Node VM доказательством совместимости. Внутренние переменные bridge не передавать в wrapper; это уменьшение случайных повреждений, НЕ sandbox.

### 3. Очередь, отмена и владение — главная сложность

Переиспользовать OperationJournal и выделить минимальное общее управление очередью из BatchExecutor. Сохранить batch callbacks prepare/readExpected/record/verify. Не оформлять скрипт фиктивным batch-шагом: его изменения не наблюдаются `record`.

Все execute считаются потенциальной записью. В один момент выполняется один batch или execute; навигация и прочие запросы документа также не должны вмешиваться в execute, кроме статуса/отмены и служебных сообщений. Повтор fingerprint включает исходный язык, code и args, а не только скомпилированный текст; имя команды разделяет batch/execute. Исходный scope не подменяется при reconnect. Status/cancel обслуживают оба вида по operationId, batch-output сохраняет прежнюю форму.

`execution.yield()` отдаёт управление UI существующим механизмом, затем проверяет отмену, scope и deadline. Серверный timeout — только срок ожидания. Он даёт unknown, сохраняет активный слот и не запускает повтор. Stop снимает разрешения и отменяет очередь; активный код прекращается лишь при сотрудничестве. Синхронный цикл может блокировать и обработку Stop.

При потере владельца во время активного скрипта daemon/listener должны удерживать блокировку передачи, даже если сокет уже закрыт. Новый владелец получает SESSION_BUSY; после незавершённого исполнения в потерянной связи допускается восстановление только новой plugin-сессией. Reconnect не является доказательством остановки. Обновление generation не обезвреживает настоящий объект figma, уже захваченный скриптом.

Обязательное правило для доверенного скрипта: await всей работы, не оставлять listeners, callbacks или detached promises, не заменять `figma.ui.onmessage` и не вызывать `closePlugin`. Это договор доверенного кода, не техническая защита. После нарушения требуется перезапуск plugin main; полное принудительное обеспечение относится к контролируемому режиму.

### 4. Результат без выдуманных гарантий

Новый discriminated результат execute: идентификаторы, `kind: 'execute'`, status, value или resource, logs, warnings, error `{code, phase, message, line?, column?, recoveryAction}`, `effects: 'none'|'unknown'`. `none` разрешён только до запуска кода; после запуска — unknown даже при успешном return. `succeeded` означает завершение async wrapper и упаковки ответа, а не verified layout. Ошибка сериализации после записи не превращается в «ничего не применено».

При обычном завершении/исключении можно отделить Undo через `commitUndo`; проверить в Desktop и не заявлять атомарность. Не вызывать `triggerUndo` автоматически. Ошибка Undo фиксируется отдельно, без потери исходной ошибки.

Return поддерживает только JSON DTO: конечные числа, строки, boolean, null, массивы и обычные объекты. Undefined на верхнем уровне нормализуется в null; циклы, BigInt, функции, symbol, API nodes и accessors отклоняются с RESULT_NOT_SERIALIZABLE. Нужны ограничения глубины/числа элементов до полного сериализованного накопления. Произвольный Proxy способен нарушить даже сериализацию — ещё одна граница доверия.

Предлагаемые стартовые пределы: исходник 32 KiB UTF-8, args 8 KiB, общий command <= существующих 64 KiB после преобразования, полный inline-ответ <=32 KiB, результат-ресурс <=256 KiB, логи <=8 KiB/100 записей, глубина DTO 32, не более 10000 значений. Все пределы проверяются по фактическому размеру оболочки. Превышение размера компилированного запроса отклоняется до запуска; oversized result после выполнения сообщает об ошибке результата и unknown effects.

Ресурсы используют `figma-resource://execution/...`, MIME application/json, TTL 60 секунд, максимум 16 записей/4 MiB на сессию. Расширить существующее хранилище минимально, сохранив строгие export MIME/schema; JSON передавать ограниченными chunks, проверяя порядок, суммарный размер и deadline. Удалять при смене сессии/владельца. Наличие URI не даёт права читать чужие результаты. Не сохранять код/args/result/logs на диск по умолчанию; штатная диагностика хранит IDs, фазу, объём, время и code. Не обещать фильтрацию произвольных секретов, которые доверенный скрипт сам прочитал и вернул.

### 5. Каталог без раздувания tools/list

Статический индекс и ресурсы по типам/членам: `figma-api://index`, `figma-api://types/...`; имена и размеры проверяются, пути клиента не используются для чтения filesystem. Первый вариант — разбиение закреплённого d.ts по декларациям с проверками результата генерации, без универсального генератора обработчиков. Отдельные короткие заметки: dynamic-page, async access, loadFontAsync, figma.mixed, instance restrictions, bindings и отмена. Неподдерживаемый синтаксис генератора должен останавливать сборку, а не терять декларации молча.

Контекст возвращает версии и возможности среды; статические объявления и проверенные feature probes разделены. Сам факт существования метода не доказывает, что он допустим для любого узла/режима. Runtime probe не выполняет мутации ради обнаружения API.

Два обязательных примера: статистика уникальных комбинаций шрифта/размера/lineHeight по сегментам; выбранный раздел с экземплярами карточек, отчётом overrides, допустимыми layout-изменениями и bindings. Для запрещённой реструктуризации внутри instance возвращать понятный пропуск, не делать скрытый detach.

## Risks / Trade-offs

- [Зависание main thread] → проба на конечном длительном цикле в отдельной fixture, честная инструкция ручного восстановления; не запускать бесконечный цикл в рабочем файле.
- [Поздняя запись после disconnect/return] → удержание владения для незавершённого wrapper; правила отсутствия фоновой работы; для гарантированной защиты нужен другой режим.
- [Prompt injection в документе] → содержимое документа остаётся данными, не должно автоматически превращаться в исполняемый код или расширять разрешения.
- [Неизвестные изменения] → effects=unknown, reread нужных узлов; batch сохраняется для проверяемых операций.
- [Ресурсы/логи содержат данные документа] → session ownership, TTL, лимиты, отсутствие постоянной записи по умолчанию.
- [Дрейф типов и Desktop] → фиксировать версии и evidence, повторять минимальные пробы при обновлениях.

## Migration Plan

Сначала Desktop spike, затем контракты/очередь, runtime, ресурсы, каталог и приёмка. Версия wire protocol 2 требует обновить сервер и plugin вместе; конфигурация stdio и pairing не меняются. Старые exports и batch сохраняют внешний контракт. При rollback остановить собственный bridge штатно и вернуть обе сборки; изменения документа автоматически не откатываются.

До реализации скорректировать действующий архитектурный контекст и явно связать заменённые положения прежних changes. Если к тому времени появятся main specs после архивации MVP, оформить точные MODIFIED deltas к ним, не создавать дубликаты.

## Оценка и порядок поставки

Инженерная оценка для одного разработчика, знакомого с репозиторием; это диапазоны, не обещание календарного срока:

| Этап | Трудозатраты | Выход |
| --- | --- | --- |
| Desktop spike и JS vertical slice | 2–4 дня | Проверка механизма и демонстрация, ещё без готовности к повседневной работе |
| Контракты, общая очередь, permissions, lifecycle/ownership | 3–5 дней | Нет повторного запуска и обычной конкуренции с batch |
| TS, ошибки, bounded JSON/logs/resources | 2–4 дня | Пригодный для агента результат и диагностика |
| Каталог, примеры, регрессии и Desktop acceptance | 3–5 дней | Проверенное покрытие двух пользовательских сценариев |
| Итого доверенный режим | 10–18 рабочих дней | Примерно 2–4 недели при доступности Desktop-проверок |

Контролируемый режим: предварительно ещё 4–8+ недель на ограниченный поднабор, низкая уверенность до отдельного spike. Он требует интерпретатора/инструментирования, непрозрачных handles вместо настоящих nodes/figma, посредника для каждого API-вызова, read/write policy, учёта операций/памяти/await и тестов обхода. Инструментирование циклов само по себе не останавливает тяжёлый синхронный вызов Plugin API. Полная совместимость со всем Plugin API в этот диапазон не обещается; такой этап не блокирует доверенную поставку.
