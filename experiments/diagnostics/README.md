# Единый диагностический плагин

Импортировать: `G:\Projects\AI\Figma-plugin-mcp\experiments\diagnostics\manifest.json`.

Сборка: `npm run build:diagnostics`. В тестовом файле нажмите «Запустить все проверки». За один запуск собираются локальные ресурсы, чтение/PNG и ещё один замер с автоматическим Stop через 500 мс после начала. Скопируйте общий отчёт. Существующие отдельные стенды сохранены для воспроизведения прежних результатов; новые проверки добавляются сюда.

Stop не прерывает синхронный API или экспорт, а останавливает последующие участки работы. Автоматический замер Stop проверяет создание фикстуры; он не подтверждает задержку остановки внутри экспорта. Закрытие плагина может оставить созданные объекты. Ошибки и очистка включены в отчёт. Лимиты предварительные.

В `read` дополнительно измеряются `yieldMs` (ожидание между порциями), `yields` (число ожиданий), `workMs` (остальное время). Новая сборка использует `scheduler: ui-message`: main отправляет yield с ID, UI возвращает его, main продолжает только после совпадающего ID. Внутри создания фикстуры и чтения таймеры больше не используются. Задержки доставки UI-сообщений всё ещё возможны; производительность новой сборки требует Desktop-проверки. Старые отчёты без scheduler относятся к таймерному варианту.

`boundaries` проверяет лимит одного узла, глубину 0, точный байтовый предел первой строки и предел на байт меньше на той же фикстуре без повторного создания фигур.

## Проверка границы документа и сессии

Используйте два отдельных **тестовых файла A и B** с разными отображаемыми именами. Имя помогает читать отчёт, но не является идентификатором документа. Проверка создаёт один прямоугольник `FIGMA_MCP_DIAGNOSTIC_MARKER` в текущей странице A; после проверки его можно удалить вручную. На текущих страницах A и B заранее не должно быть других объектов с этим именем. Файлы должны быть открыты в Figma Desktop на целевой ОС. Эта проверка использует диагностический режим с записью только маркера; production-сборка по-прежнему сообщает `writeEnabled=false`.

1. В корне проекта выполните `npm run build:diagnostics`. Остановите другие серверы на порту 55263. В отдельном терминале запустите `node dist/diagnostics/controller.js` и оставьте процесс работать на протяжении **всех** следующих шагов. Он выведет путь к временному файлу сопряжения; скопируйте его содержимое в поле секрета диагностического плагина. Сам секрет не включайте в отчёт.
2. В файле A импортируйте и запустите указанный выше manifest диагностики. Проверьте имя документа, подключитесь, нажмите «Снимок маркеров» и убедитесь, что `markerIds` пуст. Нажмите «Записать тестовый маркер», дождитесь события `positive` со статусом `succeeded` и снова снимите маркеры: должен появиться один ID. Скопируйте журнал событий в отдельный текстовый отчёт.
3. Не закрывая плагин, отключитесь и подключитесь снова к тому же процессу. Нажмите «Проверить старую команду». Ожидаются `replay-sent` с разными поколениями и затем `rejected` с `layer:ui`, `code:SESSION_EXPIRED`. Сохраните журнал; повторно подключитесь и снимите маркеры: набор ID должен остаться прежним.
4. Оставив плагин и соединение работающими в A, переключитесь на вкладку B. Зафиксируйте, остался ли UI плагина открытым. Если UI доступен, снимите маркеры и сравните свежие `documentLabel`, `sessionId` и `connectionGeneration` события `snapshot` с предыдущим снимком A; строка имени над кнопками обновляется только при соединении и сама по себе не подтверждает смену документа. Затем нажмите «Проверить старую команду», сохраните отказ и после переподключения снова снимите маркеры: в B список должен оставаться пустым. Если Figma закрывает UI при смене вкладки, запишите это наблюдение и продолжите следующий шаг. Если снимок всё ещё относится к A либо невозможно определить документ работающего main, не выдавайте его за снимок B или доказательство границы.
5. Вернитесь в A, закройте плагин, если он ещё работает, и заново запустите тот же manifest, не перезапуская сервер. Подключитесь, снимите маркеры, нажмите «Проверить старую команду» и сохраните новый журнал. Ожидаются новая сессия и отказ старого envelope; повторный снимок после переподключения должен совпасть с предыдущим. Журнал UI живёт только до закрытия плагина, поэтому копируйте его перед каждым перезапуском.
6. Закройте плагин в A, откройте B и запустите тот же manifest. Подключитесь и снимите маркеры: список должен быть пуст. Нажмите «Проверить старую команду», сохраните отказ, переподключитесь и снова снимите маркеры: список должен остаться пустым. Сохраните журнал B и подтвердите отсутствие нового прямоугольника визуально.
7. Передайте журналы A и B и версии Figma Desktop/ОС. Завершите сервер в терминале через Ctrl+C и удалите маркер из A. Не заменяйте отказ UI заявлением о том, что устаревшая команда дошла до main: событие `layer` указывает реально проверенную границу. Отсутствие или наличие `fileKey` не используется как основание идентичности.

Диагностический manifest использует те же `documentAccess` и `networkAccess`, что и production manifest; однако тест выполняется диагностической сборкой с явно включённым маркерным обработчиком. Отчёт не подтверждает включение production-записи, работу других операций или поведение production manifest вне проверенных полей. Если положительная запись, отрицательный отказ или сравнение снимков не выполнены, 1.2 остаётся открытой.

Общий runtime дополнительно сравнивает объект `figma.root` с объектом, полученным при старте. Это защитный признак, а не доказанная идентичность файла: Figma может переиспользовать один proxy для разных документов или выдавать новый proxy для того же документа. При неожиданном `DOCUMENT_MISMATCH` не обходите проверку; сохраните отчёт и оставьте 1.2 открытой.
