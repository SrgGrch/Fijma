# Совместимость: начальная проверка

Дата: 2026-11-03. Проверено на Windows NT 10.0.26300, Node.js 22.23.2, npm 11.11.0. Установлен Figma Desktop 126.10.13.

Зафиксированы MCP TypeScript server/client 2.4.0, esbuild 0.28.2 и Figma plugin typings 1.142.0 в package-lock.json. Контрактный клиент — MCP TypeScript SDK client 2.4.0; его поддержка изображений и ресурсов ещё не проверялась. Требование runtime SDK: Node.js 20 или новее.

Команды из корня проекта: `npm ci`, `npm run build`, `node tests/smoke.mjs`. Чистая установка и сборка прошли; клиент подключился к серверу через stdio и получил пустой каталог. Это каркас, а не каталог инструментов MVP.

Manifest сборки: `dist/plugin/manifest.json`. Пользователь подтвердил успешный импорт текущей версии и открытие окна плагина в Figma Desktop. Первая попытка с `ws://127.0.0.1:3845` была отклонена валидатором manifest; текущий предварительный адрес — `ws://localhost:3845`. Сетевое соединение, обмен сообщениями main/UI, границы документа, Undo, ресурсы, лицензия, лимиты и экспорт ещё не проверены.

До реализации записи необходимо выполнить эксперимент задачи 1.2 на отдельном тестовом файле. При невозможности надёжно изолировать документы транспорт блокируется до принятия решения.

Дополнение к 1.2: порт 3845 занят другим процессом. Для отдельного диагностического стенда выбран 55263; Node WebSocket-клиент получил probe и передал ответ через loopback. Figma Desktop, политика manifest и граница документов в этом опыте ещё не проверены.

Пользователь подтвердил в Figma Desktop: диагностический плагин показывает «WebSocket подключён», получает ответы через main (пример: ответ 3) и сообщает `fileKey доступен: false`. Это подтверждает связность и работу диагностического обмена без fileKey; переключение документа и отклонение устаревших команд пока не проверены.

При переключении на другой файл и обратно пользователь сообщил, что окно диагностики осталось открытым и идентификатор сессии не изменился. Это наблюдение не устанавливает, к какому документу обращается main во время переключения, и не доказывает защиту от устаревшей записи.
Пользователь также подтвердил, что номер ответа продолжал расти на другой вкладке: обмен с исходным main продолжался в фоне.
Пользователь подтвердил: после закрытия и повторного запуска диагностического плагина идентификатор сессии изменился, соединение восстановилось. Это не является проверкой отклонения старых команд.

Пользователь проверил отдельный диагностический обработчик в двух тестовых документах: команда с идентификатором старой сессии вернула `SESSION_EXPIRED`, контрольная запись создала прямоугольник. Локальный `node tests/session-probe.mjs` также проверяет отсутствие вызова создания для старой сессии и создание для текущей. Проверка выполнялась через UI экспериментального плагина, а не через очередь будущего сервера; маршрутизация и отбрасывание старых сетевых команд рабочего моста ещё не доказаны. Поэтому 1.2 остаётся открытой до проверки полной транспортной границы.

## Undo: проверка Desktop (задача 1.3)

Окружение: Windows NT 10.0.26300, Figma Desktop 126.10.13. Пользователь выполнил в тестовом файле три сценария диагностического плагина: два пакета с `commitUndo`; имитацию частичного шага после создания прямоугольника и `commitUndo`; пакеты с ручной фигурой между ними. По сообщению пользователя, Undo работает строго в обратном порядке во всех случаях. Это наблюдение не доказывает транзакционную изоляцию и не распространяется автоматически на другие версии или конкурентные правки.

Диагностический плагин вызывает `commitUndo` после каждого создания; частичный шаг имитирует остановку после выполненного изменения, а не реальное исключение внутри Plugin API. Автоматическая проверка вызовов: `node tests/undo-probe.mjs`.

Проверка 1.4: на синтетических PNG и SVG MCP TypeScript SDK client/server 2.4.0 через stdio передали PNG image block и SVG resource с побайтным совпадением. Экспорт из Figma и отображение у агента ещё не проверены; SDK-клиент сам по себе не является агентом.

## Экспорт и MCP (задача 1.4)

Пользователь подтвердил экспорт PNG и SVG из Figma Desktop 126.10.13 диагностическим плагином. Найденные файлы `figma-probe.png` (344 байта) и `figma-probe.svg` (152 байта) из Downloads прошли `node experiments/export-probe/mcp-client.mjs <png> <svg>`: SDK client/server 2.4.0 через stdio передали PNG image block и SVG resource без изменения данных. PNG также открыт агентом локально и визуально представлен светло-серым прямоугольником.

Ограничение: выбранный SDK client — программный контрактный клиент, а не агентский host; передача изображения непосредственно модели через MCP этим экспериментом не подтверждена. Проверенный доступный путь визуального получения — скачать PNG из плагина и открыть локальный файл. SVG получен как MCP resource и локальный файл; визуальная интерпретация SVG не проверялась. Транспорт этого эксперимента не является реализацией продакшн-экспорта.

## Локальные ресурсы: подготовка задачи 1.5

Добавлен диагностический плагин `experiments/resources-probe/manifest.json`; инструкция воспроизведения — в соседнем README.md. Автотест `node tests/resources-probe.mjs` проверяет успешный сценарий, отказ второго режима и удаление созданных ресурсов в обратном порядке с подставным API. Фактическая доступность на лицензии Figma Desktop ещё не проверена; задача 1.5 остаётся открытой.

### Результат Desktop по отчёту пользователя

Пользователь передал отчёт запуска resources-probe: создание локального component и instance успешно; создание и чтение PAINT, TEXT, EFFECT и GRID стилей успешно; коллекция и FLOAT-переменная читаются обратно со значением 120 в исходном режиме; alias возвращается как VARIABLE_ALIAS; bind/unbind ширины подтверждены повторным чтением. Все 10 созданных объектов удалены без ошибок.

Добавление второго режима отклонено: `Error: in addMode: Limited to 1 modes only`. В проверенном файле доступен один режим. Это наблюдаемое ограничение текущего окружения, а не установленное название тарифа или универсальное ограничение API. В рабочем обработчике такой отказ должен возвращаться как CAPABILITY_UNAVAILABLE без создания запасной коллекции или подмены переменной константой.

Задача 1.5 выполнена в пределах проверки доступности перечисленных API. Применение значений всех видов стилей, остальные типы переменных, полный CRUD и сохранение связей существующего экрана остаются предметом группы 8. Версия Desktop, ОС и название тарифа в новом отчёте не указаны; ранее записанное окружение не перепроверялось.

Разброс времени чтения 161–19987 мс не позволяет обещать стабильную задержку на текущих параметрах. В следующую сборку того же плагина добавлены раздельные измерения времени ожидания между порциями и остального времени обхода, а также граничные проверки depth/node/byte. В диагностическом обработчике таймерная уступка заменена на коррелируемый main→UI→main обмен, который возвращает управление циклу сообщений и сохраняет проверку Stop между порциями. Автотест проверяет обмен без таймеров, игнорирование чужого yield ID, Stop и очистку. Улучшение времени и задержки Stop в Desktop новой сборкой пока не измерено; они не объявляются гарантированными. Новые ручные прогоны будут объединяться с последующими проверками в том же плагине.

Добавлены общие входные схемы десяти инструментов, stdio-каталог, защищённый файл сопряжения и loopback listener. Нативный Windows-тест проверил ACL каталога (защищён от наследования, одна разрешённая SID), неверный секрет, Origin, второй плагин, лимит ожидающих соединений, размер первого сообщения и таймаут. SDK-клиент проверил схемы, structuredContent, tool/protocol errors и повторный вызов после ошибки. Задачи 2.2/3.1 завершены; полные схемы результатов и конечные поля 2.1, все границы 2.3 остаются в работе.

Контекст и дерево подключены через stdio → настоящий loopback WebSocket → код UI → собранный main. В сквозном автотесте Figma API подставлен: пустая страница, актуальное выделение, отсутствие fileKey, SESSION_EXPIRED для старой сессии и CAPABILITY_UNAVAILABLE для неподключённого экспорта проверены. Отдельный тест загрузки страницы подтверждает отсутствие обхода остальных страниц и изменения текущей страницы/selection. Это основание закрыть 4.1 по автоматическим критериям, но не Desktop-приёмка 1.2/10.1.

Дерево получает cursor с session/generation/query/revision/TTL; тесты проверяют продолжение без пропусков, смену области, ревизии и истечение. Поиск ещё не подключён, поэтому 4.2 открыта. Bootstrap-пределы ограничены handshake, контекст публикует их как текущие защитные значения, а не измеренные гарантии. Изменения документа недоступны, writeEnabled=false. Новый основной плагин в Desktop пока не запускался; Computer Use не применяется.
